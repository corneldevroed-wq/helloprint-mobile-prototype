Prototype + Design System

One repo (Helloprint/helloprint-design) with two folders. The design system stands on its own; the prototype builds on it. The style guide keeps its live cut-outs from the prototype pages, because both are served from the same address.

Names

FolderWhat it isWhy this name
design-system/Tokens, components (CSS + the bit of JS they need), icons, the UI Style Guide as its index.htmlSays what it is; the page itself stays "UI Style Guide".
prototype/Every page, the page layouts, products and help data, photosNot "website": developers read that as the production code. This is the clickable redesign.
sketches/The 31 sketch pages (A/B/C overviews)Our record of choices; out of the way of both.

The structure

helloprint-design/
  index.html            → opens prototype/ (the tester link keeps opening the home)
  CLAUDE.md  README.md  docs/
  design-system/
    index.html          the UI Style Guide (now design-system.html)
    tokens.css          :root — colours, corners, type sizes, line heights
    components.css      base (body, h1, h2, p) + every component: buttons, pills, fields, badges, cards, options,
                         accordion, tabs, sheet, toast, tooltip, radio rows… mobile and .desk rules together
    components.js       badgeHtml, sheets, toast, accordion, tooltip, field errors
    icons/              material icons, UI icons used by components
  prototype/
    index.html  product.html  cart.html  help-centre.html …   (17 pages)
    pages.css           page layouts + page-specific tweaks of components (".selection .btn")
    app.js              shell (header, footer, menu, search), cart, VAT, delivery dates, home data
    products.js  help-data.js  help-content.js
    ../prototype/assets/             photos, menu and category images
  sketches/

A prototype page loads ../design-system/tokens.css, components.css, components.js, then its own pages.css and app.js. The style guide loads only the design-system files: if a component looks wrong there, it is missing from the design system. That is the proof it is really isolated.

How deep: three options

A · LightOnly the guide and tokens.css move to design-system/; all component CSS stays in the prototype. Quick, but not isolated: the guide still needs the prototype's CSS.
B · Components out (my pick)Tokens, components and their JS move; pages keep layout and tweaks. The guide runs on the design system alone. One CSS file per side keeps it dead simple.
C · PackageB, plus one file per component and a versioned package developers install. Needs a build step; makes sense when development starts using it, not now.

About 300 of the page rules are the mobile PDP versions B–I (behind the Flow switch). They move as they are; once you choose a flow they can go, and pages.css gets a lot shorter.

How it keeps working as we add to the prototype

  1. New thing that can appear twice (a button, a card, a label) → design-system/components.css + a row in the guide, in the same commit.
  2. Only for one page (the PDP grid, the cart sidebar) → prototype/pages.css.
  3. A component looks different on one page → a scoped rule in pages.css; if it becomes the new default, it moves into the design system.
  4. One cache version for both folders (one sed over */*.html), as now.

Links

Every page gets a new address (/product.html → /prototype/product.html). The old addresses get a tiny page that forwards with the same ?p=…, so links already shared with testers keep working, in both repos.

Order of work

  1. Move the files into the folders and fix every path (nothing changes visually).
  2. Split styles.css and app.js as above.
  3. Check: every page at 390 and 1512 against a snapshot from before, every computed style and position, 0 differences; the guide on its own.
  4. CLAUDE.md, components.md and decisions.md follow the new structure.
  5. Later (step 4): GitHub Pages on the Helloprint repo, then the new tester link.

No other session may work during 1–3: every file changes.

My pick: B, with the names design-system/ and prototype/. It isolates the design system for real (the guide runs on it alone), stays without a build step, and the rule "reusable → design system, one page → prototype" is the same question you already ask when we add something. C can come later on top of B, when development wants a package.
